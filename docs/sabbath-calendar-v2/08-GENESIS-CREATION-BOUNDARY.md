# 08 — Genesis Creation Boundary

## 8.1 Two modes

### Mode A — Unbounded mathematical chronology

**This is the engine.** For every accepted integer `n`, `SabbathJDN(n)` is defined. There is no first `n` inside the core. Sabbath #1 is an index origin, not a claim that indexing begins at Creation.

Mode A is **PROJECT-DEFINED** arithmetic. It is exact on its own terms. It does not say that people observed the Sabbath on each of those days.

### Mode B — Optional Creation-bounded interpretation

A later, clearly labeled overlay may propose that the seven-day sequence has a first Sabbath of interest: the seventh day of the Creation week in Genesis. Mode B is not loaded in MVP. It is not a constant in `src/chronology/`. It cannot change `ANCHOR_JDN`.

Mode B is **UNRESOLVED** as a date and **PROPOSED** only as a slot where a date could be attached after a separate owner approval.

## 8.2 What this document will not do

- It will not name a year, JDN, or Sabbath number for Creation.
- It will not average published chronologies into a “best” date.
- It will not treat Genesis 1 as a number that the formula can finish by itself. The text does not state an absolute year.
- It will not mark deep negative Sabbaths as “before Creation” or “invalid”. Under Mode A they are ordinary integers.

Any future number requires an explicit owner decision that cites the model it came from and labels the result theological or historical interpretation, not MATHEMATICALLY DERIVED from Sabbath #1.

## 8.3 What can be said without inventing a date

**Genesis Creation week (biblical text).** Genesis 1:1–2:3 describes six days of creating and a seventh day on which God rested. The project already treats Saturday as the seventh day of its week cycle. Identifying that literary seventh day with a unique absolute JDN requires a chronology of the rest of the Bible and of external history. The text of Genesis 1 alone does not provide a JDN. **Label: historical/theological source, not a date.**

**Biblical genealogies.** Genesis 5, Genesis 11, and later regnal lists have been added up by many readers. The sums depend on textual tradition (for example Masoretic, Samaritan, Septuagint), on whether numbers are complete or schematic, and on how they join to fixed points such as the fall of Jerusalem or the reign of a named king. Different choices move the result by centuries. This design does not pick a text tradition. **Label: UNRESOLVED. Do not compute a sum here.**

**Historical chronology traditions.** Well-known Christian and Jewish chronological works propose Creation epochs that differ from each other. Examples of the *kind* of tradition, named so the owner can look them up, not endorsed:

- Masoretic-based counts used by some later Christian chronologists (often associated with dates in the 5th millennium BCE).
- Septuagint-based counts, often earlier by more than a thousand years.
- The traditional Jewish *anno mundi* count used by the calculated Hebrew calendar’s year numbering, which is an epoch of that calendar system, not a result of Sabbath #1.

No year from these traditions is copied into this document as the project’s Creation date. Putting one in a table as “the” date would violate the brief.

**Proposed Creation dates.** They exist in the literature and they disagree. Disagreement is the finding. **Label: historically reconstructed when an author publishes a date; not project data.**

**Anchor independence.** Even if a Creation date were approved later, Sabbath #1 would remain JDN 1,733,205. A Creation Sabbath would be some other integer `n_c` with `SabbathJDN(n_c)` computed from the same formula. The anchor would not move to Creation.

## 8.4 If the owner later approves a bounded model

The overlay would be a separate module:

```text
src/interpretation/creation-boundary.ts
```

Inputs, all required before the module may return a number:

- A model id string.
- A citation.
- The proposed Sabbath number or absolute day, entered by the owner, not generated by a model.
- An uncertainty class, which cannot be `mathematically-exact`.

Behavior:

- The core stays Mode A.
- The timeline may draw a labeled marker “Creation boundary (model id)” at that day.
- Sabbaths numerically below that marker remain calculable. The UI may dim them only when a view setting “shade outside Mode B” is on, default off.
- Turning the overlay off removes the marker and the shading. Indexes do not change.
- The proof card does not list the Creation date as a verification input.

Acceptance for that future change: a test proves `SabbathJDN(1)` is still 1733205 when the overlay is on.

## 8.5 Relationship to negative numbering

Negative `n` means “this many weeks before Sabbath #1”, not “this many weeks before the world”. Readers will be tempted to equate the two. The UI copy for far-negative jumps should say:

```text
Sabbath #n is an exact index on the project’s seven-day line.
It is not a claim about Creation.
```

That sentence is **PROPOSED** UI copy.

## 8.6 Research questions left open

These are **UNRESOLVED** on purpose. They are not implementation tasks for MVP.

1. Which textual tradition, if any, the owner wants studied.
2. Which external synchronisms the owner is willing to treat as historically documented.
3. Whether a Mode B marker is desirable at all.

Until those are answered, the chronology the software implements is Mode A only.
